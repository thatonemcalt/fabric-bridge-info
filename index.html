How it works

Everything runs inside one JVM agent that attaches before the server starts. Scroll to watch a mod go through it.

Fabric modftb-essentials.jar
Paper / Purpur serverMinecraftServer

target class exists fields & methods match signature validated 1 skipped — target absent · vanilla path kept
main entry → bootstrap phase server entry → datapack phase
✓ degraded: axiom — one part off, everything else keeps running

The mod is read, never installed

Every class is loaded straight from the jar and rewritten in memory. Intermediary names like class_1909 become the official names the server actually uses — the remap is checked against the live server classes.

Mixins are checked before they inject

Each mixin's target class, field, and method is verified against the real runtime first. Anything that exists is applied; anything that doesn't is skipped with a one-line reason instead of crashing the server.

The mod runs where a mod should run

main entry points run during Paper's bootstrap phase, server entry points during datapack discovery. Registry windows are opened around both, so registration behaves like it would on Fabric.

And if something can't work?

One calm line in the log, the full stack in .reports/, and the rest of the mod list keeps running. A degraded mod is never a broken server.

Get the jar from Modrinth

Download FabricBridge on Modrinth and drop the jar into your server's plugins/ folder. Nothing else is installed, and nothing is required on your players' clients — a vanilla client can join. Client mods are optional: a player who wants a mod's custom items and textures installs that mod's client half.

plugins/FabricBridge-1.0-mc1.21.11.jar

Self-managed host? Add one flag

If you control the startup command, attach the agent before -jar so it loads before any server class.

java -javaagent:plugins/FabricBridge-1.0-mc1.21.11.jar -jar server.jar nogui

Managed host with a fixed startup line?

Many online server providers don't let you edit java arguments. You don't need to: on first boot FabricBridge auto-patches the server's own launch so the agent attaches by itself.

upload → restart  nothing else to configure

Drop your Fabric mods in & start

The agent creates the mods folder on first boot. Put Fabric server-side mods there, start the server, and read the boot summary line in the log.

First boot prints a summary line: how many mods loaded and which ones degraded. If something on this list shouldn't be there, check /fb why <mod> or the console demo.

Before you start

  • Java 21 or newer. The bridge and its agent target Java 21 bytecode; older runtimes are refused at startup.
  • A Paper or Purpur 1.21.11 server. This build targets 1.21.11 and its mappings; the plugin declares that API version, so a different server version will not load it.
  • Server-side mods only. Client mods, client entry points and client-only classes are detected on a dedicated server and skipped, not forced in.
  • One outbound HTTPS request on first boot. The official Mojang mappings are downloaded once and cached under plugins/FabricBridge/cache/.

Command reference

The full /fabricbridge and /fb tree as shipped.

/fabricbridge · /fbRoot command. Opens the overview: active mod count, degradation list, links to each report view.
/fb helpLists every subcommand.
/fb statusRuntime census: mods loaded, mixins applied or skipped, failures this session.
/fb mods [page]One line per mod with its state: fully active, degraded, or not loaded.
/fb degradedOnly the degraded mods. Each line tells you to run /fb why for the reason.
/fb notloadedMods that never reached load: dependency problems, stated as sentences.

/fb skipped [page]Every concrete preflight-skipped mixin with its reason.
/fb failedmixins [page]Cases where Mixin itself threw during apply; the affected class is skipped and the mod continues.
/fb failures [page]All recorded failure records in one place.

Compatibility

What to expect, stated plainly, no distributor promises.

v1.0 — verified on Purpur 1.21.11 and Paper 1.21.11 · joins proven from 26.2 and 1.21.9 clients via ViaVersion

Most Fabric server-side mods work. Not all of them will.

The bridge is built to run mods without modification, and the majority load and behave normally. Some mods include code pieces that cannot exist on a Paper-family server. In those cases the affected part is skipped and the reason is printed at boot.

A degraded mod isn't a broken server. The rest of the mod list runs normally, the failing detail is recorded to .reports/ for anyone who wants the full stack, and the console shows the same facts through /fb why.

Verified scope: Purpur 1.21.11-2568 with Fabric API 0.141.6, Lambda 1.4.0 and Lithium 0.21.4 — clean boot, real protocol joins, mod commands, mod whispers, and ViaVersion / ViaBackwards joins from a 26.2-claiming and a 1.21.9-claiming client. Paper 1.21.11 build 132 was also tested end to end — clean boot, 41 mods, protocol joins and no crash reports.

  • Every degradation is reported once, in a sentence, not a stack trace
  • Skipped mixins always include a reason and never take the server down
  • Client-only entry points are detected on a dedicated server and step aside
  • Players on newer (26.x) or older (1.21.9/1.21.10) versions can join via ViaVersion / ViaBackwards
  • Mods that need runtime loaders (e.g. those with their own bootstrap machines) are the main unmapped surface

Support

Reports go to GitHub issues — the same templates are linked from the Modrinth page. Pick the right one so the details arrive with the report.

Bug report

A crash, a tick error, or wrong behavior. The form asks for the server build, bridge version, boot summary line, and any .reports/ file that is on-topic.

Feel free to report bugs — we always expect them on mods we haven't tested yet.

Degradation report

A mod that went quiet. The form asks for the full output of /fb why <mod>, which is the bulk of the diagnosis.

Question

Anything else: installation, the command surface, whether a given mod will work, or how a mechanism above operates.

Frequently asked

The server booted but a mod says "degraded" — is the server broken?

No. One mod switched off a piece of itself with a reason. Everything else runs normally. /fb why <mod> shows which parts of that mod remain active.

Why did a mixin get skipped?

The mixin's declared target (a class, field, or method) does not exist on this server's build. Injecting against a missing target would crash classloading, so the bridge leaves it out. Any code from the mod calling into that mixin is routed back to vanilla behavior.

Do I need a Fabric server alongside Paper?

No. FabricBridge performs the remapping and class loading itself on Paper and Purpur. Setup is one jar: add the -javaagent flag on hosts you control, or nothing at all on managed panels with a fixed startup line — the jar auto-patches the server's own launch on first boot.

Where are the stacks when something fails?

In plugins/FabricBridge/mods/.reports/, one file per failure. The console intentionally shows one line; the files hold the depth.

Is there a way to test a few mods before committing a full mod list?

Yes. Mods are read from plugins/FabricBridge/mods/ at each boot, so you can build the folder up gradually and read the boot summary after every restart.

Can players join from a different Minecraft version than the server?

Yes. With ViaVersion / ViaBackwards on the server, players on newer (26.x) or older versions join normally — this is verified with full protocol-level joins, not just a ping.
