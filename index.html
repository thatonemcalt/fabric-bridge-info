FabricBridge

Load Fabric server-side mods on Paper and Purpur servers, without Fabric Loader. Put your mods in the plugin's mods folder and start the server. Mods are remapped, mixin-checked, and run during Paper's bootstrap phase.

How it works

Everything below runs inside one JVM agent that attaches before the server starts.

Class remapping

Fabric mods are compiled against intermediary names (class_1909). Paper's runtime uses official names (ItemStack). The agent rewrites every mod class at load time, then checks the result against the live server classes so Paper and Purpur patches don't invalidate the mapping.

Mixin preflight

Each mixin's target class, fields, and methods are checked against the real runtime before injection. A mixin whose target doesn't exist is skipped with a one-line reason instead of crashing the server. The mod keeps whatever still works.

Entry points

main entry points run in Paper's bootstrap phase, server entry points during datapack discovery. Registry windows are opened around these phases so mods can register attributes, sounds, and datasets the same way they would on Fabric.

When a mod can't work

The failure is caught, logged as one readable line, and written to plugins/FabricBridge/mods/.reports/ with the full stack. The rest of the mod list is unaffected. Any console command (/fb why <mod>) shows what happened and what still runs.

Installation

Works the same on Paper and Purpur.

  1. 1

    Download the jar

    Get the latest FabricBridge jar from the releases page and place it in the server's plugins/ folder.

    plugins/FabricBridge-<version>.jar
  2. 2

    Add the javaagent argument

    The agent must attach before the server classes load. Add this line before -jar in your startup script.

    java -javaagent:plugins/FabricBridge-<version>.jar -jar server.jar nogui
  3. 3

    Put your mods in-place & start

    The agent creates a mod folder on first boot. Place your Fabric mods there, start the server, and read the boot summary line in the log.

    plugins/FabricBridge/mods/  ← drop Fabric mod jars here
First boot prints a summary line: how many mods loaded and which ones degraded. If something on this list shouldn't be there, check /fb why <mod> or the console demo.

/fb mods [page]One line per mod with its state: fully active, degraded, or not loaded.

Compatibility

What to expect, stated plainly, no distributor promises.

Most Fabric server-side mods work. Not all of them will.

The bridge is built to run mods without modification, and the majority load and behave normally. Some mods include code pieces that cannot exist on a Paper-family server. In those cases the affected part is skipped and the reason is printed at boot.

A degraded mod isn't a broken server. The rest of the mod list runs normally, the failing detail is recorded to .reports/ for anyone who wants the full stack, and the console shows the same facts through /fb why.

  • Every degradation is reported once, in a sentence, not a stack trace
  • Skipped mixins always include a reason and never take the server down
  • Client-only entry points are detected on a dedicated server and step aside
  • Mods that need runtime loaders (e.g. those with their own bootstrap machines) are the main unmapped surface

Support

Tickets are GitHub issues. Use the right template so the details arrive with the report.

Bug report

A crash, a tick error, or wrong behavior. The form asks for the server build, bridge version, boot summary line, and any .reports/ file that is on-topic.

Degradation report

A mod that went quiet. The form asks for the full output of /fb why <mod>, which is the bulk of the diagnosis.

Question

Anything else: installation, the command surface, whether a given mod will work, or how a mechanism above operates.

Frequently asked

The server booted but a mod says "degraded" — is the server broken?

No. One mod switched off a piece of itself with a reason. Everything else runs normally. /fb why <mod> shows which parts of that mod remain active.

Why did a mixin get skipped?

The mixin's declared target (a class, field, or method) does not exist on this server's build. Injecting against a missing target would crash classloading, so the bridge leaves it out. Any code from the mod calling into that mixin is routed back to vanilla behavior.

Do I need a Fabric server alongside Paper?

No. FabricBridge performs the remapping and class loading itself on Paper and Purpur. The only setup step is the -javaagent argument.

Where are the stacks when something fails?

In plugins/FabricBridge/mods/.reports/, one file per failure. The console intentionally shows one line; the files hold the depth.

Is there a way to test a few mods before committing a full mod list?

Yes. Mods are read from plugins/FabricBridge/mods/ at each boot, so you can build the folder up gradually and read the boot summary after every restart.
