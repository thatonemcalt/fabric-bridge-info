Built to bend, not break

Every mechanism below exists for one reason: a mod that misbehaves should degrade while the server keeps breathing.

Full class remapping

Every mod class is rewritten from intermediary → Mojang names before it loads — then verified against the live patched server classes, so Paper rewrites and Purpur re-types can't fool it.

Mixin preflight flight-check

Each mixin is verified against reality before it applies. Structurally impossible ones are skipped with a plain-English reason — never a stack wall.

Rails-first degradation

Failing entrypoints and broken mixins route into calm per-mod reports. The server never crashes on a mod failure — that's the design contract.

Duck-interface shims

Mods talk to mixin-attached helpers through bridge dispatchers; missing pieces answer "not available" instead of exploding chunk-system workers.

Registry windows

Bespoke bootstrap windows let mods register attributes, sounds and datasets inside Paper's bootstrapper phase — the trickiest part of the bridge, done.

FabricLoader persona

Mods that probe FabricLoader (containers, objects, container probes) meet a faithful stand-in with the pseudo-mods (fabricloader & java) real loader exposes.

Console-first command UI

/fb and /fabricbridge give you a live health console: status, per-mod investigation, mixin bookkeeping — permission-gated and logical.

Per-mod .reports files

Deep failure chains are filed to mods/.reports/ as full stacks — the console stays one-line calm, details stay on disk.

Install in three moves

Copy, flag, boot. The boot digest tells the whole story on startup.

  1. 1

    Drop the jar in plugins/

    Grab the latest FabricBridge jar from our releases page and drop it into your server's plugins folder like any other plugin.

    plugins/FabricBridge-<version>.jar
  2. 2

    Add the javaagent flag

    One line before your -jar argument. FabricBridge is both a Paper plugin and an agent — the agent wires up classes *before* Paper needs them.

    java -javaagent:plugins/FabricBridge-<version>.jar -jar server.jar nogui
  3. 3

    Read the boot digest

    Every boot ends with a one-line health summary: how many mods loaded, which ones degraded, and why. Build your mods folder exactly like you would on a real Fabric server.

    FabricBridge boot summary: most mods loaded clean · degradation families: jamlib, balm…
JVM flag rounding: overhead is typically <10% and comparable to running those mods through a real Fabric server. Heavy modded setups benefit from a 2 GB+ heap and G1GC.

The honest promise

No shiny "100% compatible" sticker — here's the real shape of it.

reality check
MOST fabric mods work.
Don't expect all to.

The overwhelming majority of fabric server-side mods load and run untouched — the bridge exists to make that the default. A few mods carry pieces that genuinely can't exist on a Paper-family server (client-only code, deep platform helpers). Those degrade calmly: one readable sentence at boot, never a crash, never a stack wall.

Anything that can't work names itself and its reason in the boot digest — the rest of your mod list never feels it.

Read-first before ticketing

The server booted but a mod says "degraded" — is the server broken?

No. Degraded means that one mod's advanced part switched off with a reason; the server and the rest of the mod list run normally. /fb why <mod> explains exactly which parts of that mod stay live.

Why did a mixin get "skipped structurally"?

FabricBridge pre-checks each mixin against the real, running vocabulary of classes on your server. When a mixin claims a field or method the runtime simply doesn't have, applying it would crash the JVM classloader — so the bridge skips it and re-routes any call the mod makes to the vanilla path.

Do I need a Fabric server alongside?

No. FabricBridge remaps and loads the fabric mods itself on Paper / Purpur. If it succeeds you'll see the boot digest; the only install touch-point is the -javaagent flag.

A client mod crashed on join — is FabricBridge the cause?

Client-only entrypoints are auto-detected and degradation is calm by design. If you see a specific mod listed under /fb why with "client-only" in it, that mod was simply asked to do client work on a dedicated server — expected on any fabric compat shelf too.

Where are the big stacks when something fails?

Next to your plugins folder: plugins/FabricBridge/mods/.reports/ — one calm console line summarises, files hold depth.

Why "partially active" instead of off?

Class-init, events, and registry data still work for many degraded mods — only the failing code-path segment goes quiet. The bridge keeps whatever is provably safe and reports the remainder.
